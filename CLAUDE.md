# Notes for AI assistants working on Roj

- Never write an em dash (U+2014), en dash (U+2013) or any look-alike (figure dash, horizontal bar, minus sign U+2212, box-drawing lines) anywhere: code, comments, docs, UI strings, translations, commit messages. Use a comma, colon, "·", "to", or a plain hyphen-minus. `scripts/check-dashes.sh` enforces this in `make lint` and CI.
- In Persian and Arabic, write "Kurdish" the Kurdish way, with و: کوردی (never کردی), کوردستان, and in Arabic الكوردية, بالكوردية, كوردستان. The label "Kurdish" alone is کوردی in both. `scripts/check-kurdish.mjs` enforces it in `make lint`.
- Every interface string goes through `_()` (or `N_()` when translated later) with English as the key, and needs an entry in all four catalogs in `extension/locale/`. Check with `make i18n`.
- The engine (`extension/lib/engine.js`) and `extension/lib/tsroj.js` must stay free of GNOME imports so the CLI and tests run on Node.
- Verify UI changes in the sandboxed headless shell (`scripts/sandbox.sh`, `make screenshots`), never in the user's own session.
- When a change alters anything a screenshot shows (top bar, popup, events, settings pages, translations, fonts, colours, `roj` output in the marketing images), rerun `make screenshots` (and `make marketing` for the marketing images), look at every changed image, and commit them with the change. Fix captions that no longer match. See rule 7 in `CONTRIBUTING.md`.
- The Kurdish events live only in `extension/data/events/kurdish.json`. After editing it, or anything the website imports from `extension/lib` or `extension/locale`, run `make web` to rebuild `docs/calendar/` (the .ics files and the engine copy); `make test` checks they match. Never edit `docs/calendar/engine/` by hand.
- Branches follow git flow: `feature/NAME` from `develop`, pull request into `develop`, then `develop` into `main` for release and GitHub Pages. See rule 11 in `CONTRIBUTING.md`.
- Versioning and releases follow `RELEASING.md`.
- Account and deployment setup (extensions.gnome.org, Launchpad, keys, repository secrets) is never documented in the repo, its docs or code comments. Local notes live in `private/`, which git ignores.
- When `make test` passes locally, carry the change through without stopping to ask: push the `feature/` branch, open a pull request into `develop` and merge it with `gh pr merge --merge --auto` (GitHub merges once CI is green). Release with `make release V=X.Y.Z`, which runs the whole git flow (release branch, bump, changelog, screenshots, tests, PR into `main`, tag, Release workflow, `main` back into `develop`). Never merge on a red check: fix and rerun.
